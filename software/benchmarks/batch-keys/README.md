# Проверка пакетного перебора MIFARE Classic

Стенд сравнивает `VK_BatchKeys` (`0ab7345a`) с прежним перебором по одному ключу.
Основной код приложения и прошивка не изменяются. Карта и эмулируемые слоты не
записываются; исходный режим устройства восстанавливается после запуска.

## Результат 10 ноября 2026

На этой карте пакетирование на USB не ускорило неудачные проверки. На
телефоне Xiaomi (`2407FPN8EG`, Android 16) через Bluetooth полный проход
ускорился в **2,29 раза**, с **183,569 с до 80,040 с** (время сократилось
на 56,4%). Скорость выросла с 6,97 до 15,99 проверок/с. На USB оба метода
дали 16,64 проверки/с.

Медианы трёх повторов; время в секундах:

| Сценарий | RF-попыток | USB старый | USB пачки | BT старый | BT пачки | Ускорение BT |
|---|---:|---:|---:|---:|---:|---:|
| 32 ключа, одна пара «сектор + A» | 32 | 1,921 | 1,922 | 4,593 | 2,099 | 2,19× |
| 16 ключей, один сектор A/B | 32 | 1,921 | 1,921 | 4,624 | 2,106 | 2,20× |
| 16 ключей, 16 секторов A/B | 512 | 30,746 | 30,747 | 73,906 | 32,100 | 2,30× |
| 16 ключей, вся 4K, A/B | 1280 | 76,905 | 76,906 | 183,569 | 80,040 | 2,29× |

Во всех проходах найдено ноль ключей. Это измерение полного прохода без
успеха, а не времени до первого найденного ключа. В полном BT workflow
счётчики подтвердили 1280 одиночных аутентификаций против 16 пакетных
команд; дополнительно оба метода выполняют переключение режима и скан.
Пачки содержали по одному кандидату на 80 пар. Для 16 секторов подтверждены
8 пачек по два кандидата вместо 512 отдельных команд.

Исходные результаты: `usb.json`, `usb-onepair.json`, `usb-validation.json`,
`ble.json`; сводная статистика — `summary.json`. Параметры телефона —
`android-device.json`, журналы — `ble-benchmark.txt` и `ble-connection.txt`.
Короткий дополнительный USB-прогон на всей карте с одним кандидатом
подтвердил правильные статусы: 80 `MfErrAuth` у старого метода и один
пакетный `HfTagOk` без найденных ключей. Последующий probe подтвердил
присутствие той же геометрии карты и режим `Reader`.

Оба проекта стенда собраны без ошибок и предупреждений; языковой аудит
`ChameLab.Tools check-languages` пройден. Всего сохранено 50 измеренных
проходов: 26 USB, включая дополнительные проверки, и 24 BT.

Практический вывод: пакетирование полезно для BLE. Для USB на этом стенде
выигрыша в скорости нет. Следующее полезное изменение клиента — поиск
первого ключа большими пачками на нескольких выбранных парах, немедленное
использование найденного ключа на остальных секторах и переход к подходящей
атаке. Существующая команда прошивки уже поддерживает такую маску секторов;
перестройка порядка поиска возможна на стороне C# клиента.

## Методика

- Одна физическая карта Classic 4K, SAK `38`, 40 секторов, Chameleon на COM8,
  прошивка сообщает `v2.3.13-cl-dirty`.
- USB — настоящий `SerialTransport`; Bluetooth — настоящий мобильный
  `Mobile/BleTransport.cs`, скомпилированный в отдельный Android APK. Windows BLE
  и искусственные задержки не используются.
- Прежний путь запускается отключением **только в кэше возможностей клиента**
  команды 2012. Это существующий fallback `FindMifareKeysAsync`, который
  вызывает `Mf1AuthOneKeyBlock` для каждого кандидата. Реальные возможности
  устройства не меняются. Для полного прохода вызывается публичный workflow,
  для подмножеств секторов — те же операции аутентификации напрямую.
- Генератор `Random(73919)` даёт одинаковые шестибайтные кандидаты на обоих
  устройствах. Никаких задержек транспорта в модели нет: измеряется полное
  время настоящих команд через `Stopwatch`.
- Три повтора, порядок «старый / новый» меняется между повторами. Подключение,
  получение capabilities, прогрев и сохранение JSON не входят в измерение.
  В полном workflow входят переключение режима и проверка UID, как в приложении.
- Сценарий с 16 секторами означает первые 16 секторов **этой карты 4K**, а не
  отдельную физическую карту 1K.
- Если `FFFFFFFFFFFF` открывает сектор 0A, добавляются сценарии с этим ключом
  в начале и конце словаря. В данном опыте он не подошёл. Выводы о времени
  до первого успешного ключа поэтому являются расчётом порядка обхода,
  а не измерением успешного восстановления.
- `MeasuredTransport` считает команды, размеры пачек, байты протокола и
  статусы ответов. Неожиданные статусы прерывают измерение. Первоначальный
  `usb.json` получен до добавления этих счётчиков; отдельные короткие запуски
  служат проверкой количества команд и статусов.

## Запуск USB

Из корня репозитория:

```powershell
dotnet run --project software/benchmarks/batch-keys -c Release -- COM8 usb.json 3
```

Четвёртый аргумент — необязательный фильтр имени сценария: `onepair`,
`fullcard-1key`, `fullcard-16keys` и т. п. `--probe` только читает сведения
об устройстве и проверяет присутствие карты.

## Запуск на Android через Wi-Fi ADB

APK устанавливается отдельно от основного приложения. На Xiaomi может
потребоваться разрешить установку в системном запросе телефона.

```powershell
dotnet build software/benchmarks/batch-keys-android -c Debug
adb install --no-incremental -r software/benchmarks/batch-keys-android/bin/Debug/net10.0-android/android-arm64/io.github.m0n5ter.chamelab.batchbench-Signed.apk
adb shell pm grant io.github.m0n5ter.chamelab.batchbench android.permission.BLUETOOTH_SCAN
adb shell pm grant io.github.m0n5ter.chamelab.batchbench android.permission.BLUETOOTH_CONNECT
adb shell am start -n io.github.m0n5ter.chamelab.batchbench/crc647f210a30036712c2.MainActivity --es address CE:BA:62:C5:67:98 --ei repetitions 3
adb logcat -s BatchKeysBench:I '*:S'
adb shell run-as io.github.m0n5ter.chamelab.batchbench cat files/ble.json
```

Адрес берётся из `GetAddressAsync`, имя Activity можно проверить командой
`adb shell cmd package resolve-activity --brief io.github.m0n5ter.chamelab.batchbench`.
Фильтр сценария передаётся через `--es cases onepair`.
JSON сохраняется после каждого завершённого прохода; окончание отмечается
`BENCHMARK_COMPLETE` в logcat. USB и BLE тестируются последовательно:
одновременные команды к одному RF-полю испортят сравнение.

## Что именно ограничивает пачку

Здесь описаны параметры исходного замера. После него приложение переведено
на фиксированные пачки: 8 ключей для USB, 32 для BLE, независимо от числа
оставшихся пар. Приведённые выше времена относятся к прежним размерам пачек.

`chunkSize = min(transportLimit, max(1, 64 / pendingPairs))`.
Предел транспорта — 83 на USB и 32 на BLE. Поэтому при всех неизвестных
ключах 4K (`pendingPairs = 80`) в пачку попадает один кандидат; при 16
секторах (`pendingPairs = 32`) — два. При одной паре помещается 64 кандидата
на USB и 32 на BLE. Ответ прошивки всегда содержит 490 байт данных.

Прошивка обходит сектора внутри **каждой** полученной пачки и сообщает
результаты после её окончания. В текущем workflow переход к следующей пачке
не ставит только что найденные ключи перед остальными кандидатами словаря.

На USB после каждого неверного ключа остаётся почти вся работа с картой:
`pcd_14a_reader_reset` содержит две задержки по 10 мс, затем включение поля
ждёт ещё 8 мс. Стандартный тайм-аут обмена — 25 мс. Пакетный цикл вызывает
тот же сброс после неудачной аутентификации. В замерах выходит около 60 мс
на неудачную RF-попытку, независимо от числа команд USB.

В Android-журнале `ble-connection.txt` MTU согласован как 247 байт, затем
интервал соединения меняется с 15 мс на 47,5 мс (`interval=38` в единицах
1,25 мс), примерно через 5 секунд после подключения. Это согласуется с
`FIRST_CONN_PARAMS_UPDATE_DELAY=5000` и диапазоном 20–75 мс в
`firmware/application/src/ble_main.c`. Первый короткий старый проход
частично попал на более быстрый начальный интервал; в таблице используются
медианы трёх повторов, а исходный переход виден в сырых данных.

## Поиск первого ключа

Для ключа на позиции `j` в словаре и `P` неизвестных пар текущий обход с
пачкой из одного ключа сначала выполняет `(j - 1) * P` неудачных RF-проверок.
Если этот ключ подходит выбранной паре, последовательный поиск на ней
выполнит `j - 1` неудачных проверок. На полностью неизвестной 4K `P = 80`.
Это сравнение **числа RF-попыток до первого успеха**, а не обещание
80-кратного ускорения по времени: остаются задержки транспорта и завершение
текущей пачки. Кроме того, ключ может подходить другому сектору, поэтому
один выбранный сектор не заменяет проверку всей карты.

Практичная стратегия: небольшой общий проход частых ключей; затем большие
пачки на одной выбранной паре или небольшом числе пар до первого ключа;
проверка найденного ключа на остальных секторах; далее Nested/Static Nested
для совместимой карты. Hardnested требует отдельной оценки времени и памяти.
Полный проход словаря по всем секторам остаётся полезным отдельным режимом.

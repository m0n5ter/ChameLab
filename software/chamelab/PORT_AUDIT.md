# Проверка порта восстановления ключей MIFARE

Проверены четыре реализованных алгоритма: Static nested, Nested, Darkside и
mfkey32/Moebius. Проверены используемые операции Crypto1 из Crapto1Sharp 2.0.0,
восстановление состояний по 32 битам и обработка ответов прошивки.
Hardnested, mfkey64 и специальные RF08S-утилиты из `software/src` в этот C#-порт
не входят.

## Почему возник перебор 128 тысяч ключей

Причина Static nested — неверная семантика аргумента при вызове C#-порта.
Для nonce `009080A2` сдвиг определяется типом **известного** ключа, через
который выполнен вход: A → 160, B → 161. Тип восстанавливаемого ключа на
выбор этого сдвига не влияет.

ChameleonUltra GUI передаёт `keyType: 0x60 + validKeyType`, то есть тип
известного ключа. Наш порт передавал тип целевого ключа. Поэтому при входе
через A и восстановлении B выбирался ошибочный сдвиг 161 вместо 160.
Исправлены аргумент вызова, название параметра и тесты направления B → A.

Первоначальный вывод этого отчёта об «ограничении оригинального C» был
неверным: C проверялся с тем же неправильным аргументом, что использовал
порт. Комментарий `target key type` в C вводит в заблуждение, но реальный
вызов GUI использует `validKeyType`.

Локальный CLI из `software/script/chameleon_cli_unit.py` тоже передаёт
`type_target`; это отличается от вызова GUI и объясняет, почему запуск
локального CLI с этими аргументами не является проверкой поведения GUI.

Есть также различия отбора кандидатов между двумя C-реализациями:

- Локальный `software/src/nested_util.c` сохраняет до 50 повторяющихся
  кандидатов, упорядоченных по частоте. Старый C# возвращал только кандидатов
  с максимальной частотой, поэтому мог исключить правильный ключ с меньшей
  частотой. Новый обычный Nested соответствует локальному C.
- GUI в `chameleonultragui/src/recovery.c` использует `most_frequent_uint64`
  и тоже оставляет максимальную частоту. Следовательно, старый C# отличался
  от локального C, но этот отбор сам по себе не был отличием от GUI.

Для Static nested применяется более строгая проверка кандидата по двум
захватам. Список из 128 тысяч не отправляется на карту. Вычисления выполняются
в фоне; в GUI ту же задачу выполняет отдельный Dart isolate.

Проверена версия GUI `7311c540933e23a842db1c387334871f6f1a94ba`:
[вызов алгоритма](https://github.com/GameTec-live/ChameleonUltraGUI/blob/7311c540933e23a842db1c387334871f6f1a94ba/chameleonultragui/lib/helpers/mifare_classic/recovery.dart#L462),
[фоновый isolate](https://github.com/GameTec-live/ChameleonUltraGUI/blob/7311c540933e23a842db1c387334871f6f1a94ba/chameleonultragui/lib/recovery/recovery.dart#L324).

## Дополнительные исправления

- Для 7- и 10-байтных UID берутся последние четыре байта, как в
  `firmware/application/src/rfid/reader/hf/rc522.c:get_4byte_tag_uid`.
  Static nested теперь использует authentication UID непосредственно из
  ответа устройства, а не отбрасывает первые четыре байта ответа.
- mfkey32 отклоняет записи разных карт, блоков и типов ключа, вложенные
  аутентификации и неполные слова. Исключено молчаливое дополнение коротких
  слов неинициализированной стековой памятью. Группировка захватов в Tools
  включает UID карты.
- Разбор Nested и Static nested проверяет размер и выравнивание записей.
  Darkside проверяет статус команды и наличие данных, прежде чем считать
  карту уязвимой или обрабатывать захват.

В арифметике Darkside и mfkey32 расхождений на проверенных контрольных данных
не найдено. Результаты Darkside с чётностью и без неё, а также полные списки
кандидатов Nested сравниваются с оригинальным исполняемым C. Битовые,
байтовые и словные операции Crypto1, обратный ход и PRNG сравниваются с
независимо сгенерированными значениями C.

## Проверки

- 68 автоматических тестов проходят, включая 20 независимых векторов C.
- В контрольном векторе обычного Nested исходный C возвращает правильный
  `112233445566` вторым, после `56A908280888`. Старый C# возвращал только
  первый, неправильный ключ. Новый C# возвращает оба, как оригинал.
- На физической статической MF1K через COM8 восстановлены оба ключа всех
  16 секторов, начиная только с ключей сектора 0; прочитаны 64/64 блока.
  Ключи секторов 1 и 3 совпали с известными. Первоначальный замер после
  исправления: 18,5 секунды на восстановление и 2,3 секунды на чтение.
  Повторная проверка после остальных исправлений: 19,5 и 2,3 секунды,
  также 32/32 ключа и 64/64 блока.
- Физическая проверка в этой сессии относится к Static nested. Для обычного
  Nested, Darkside и mfkey32 использованы независимые контрольные данные C;
  это не утверждение о проверке всех типов карт и всех вариантов прошивок.

Источники и воспроизводимый генератор контрольных данных находятся в
`ChameLab.Tests/Reference/`; тесты не требуют установленного C-компилятора.
